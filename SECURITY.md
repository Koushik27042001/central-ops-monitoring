# Security

Firebase Authentication handles public email/password and Google sign-in. Verified users receive separate private workspaces when PUBLIC_REGISTRATION=true. Firebase UID is bound to the local account; inactive accounts are denied. PUBLIC_REGISTRATION=false restricts Firebase access to FIREBASE_ADMIN_EMAILS. Local password sessions remain available for private installations: salted scrypt password hashes, random session tokens stored as SHA-256 hashes, and two-day HttpOnly cookies. Firebase browser authentication supplies a recently issued ID token to POST /auth/session. The API exchanges it for a signed Firebase session JWT in an HttpOnly, SameSite=Strict cookie, Secure in production. AUTH_SESSION_DAYS=2 sets a fixed 48-hour lifetime. Protected routes verify session signature, expiry and revocation and do not accept refreshed ID tokens as a replacement. Only sign-ins from the last five minutes can create a new session. The client account UID header is checked for consistency with the authenticated cookie; it never establishes identity by itself. Mutation requests require an allowed Origin.

Mongoose strict schemas and Zod request allowlists prevent arbitrary field updates. Helmet, CORS and rate limiting are enabled. Cookie and authorization headers are redacted from logs. Credential fields are excluded from default queries; integration credential writes use AES-256-GCM with independent nonces and authentication tags. The encryption key is server/worker configuration and is never included in browser builds. Stored credentials are excluded from management responses.

Outbound monitoring pins an IPv4 DNS result for each HTTPS request and blocks private, loopback, link-local, metadata, multicast and reserved ranges. TLS certificate validation remains enabled. Redirects are not followed. Requests have timeouts and a 1 MiB response limit. Add a network egress firewall as defense in depth. IPv6 and HTTP monitoring are unsupported.

Before production, validate sessions and CRUD against MongoDB, queue retries/restarts, incident concurrency, DNS/network behavior, and browser flows. Configure least-privilege service credentials, TLS, backups, infrastructure alerts and restricted network access. Current worker writes are at least once; duplicate result samples are possible on retries. Uploads remain unavailable. Publishing only sends allowlisted saved content through an explicitly authorized per-website integration. The optional SDK requires a persistent client adapter; that adapter must enforce idempotency and content ownership.

## Workspace isolation

Background monitoring checks revalidate the website and API endpoint ownership before making requests. Publishing checks the owner of the website, blog, integration, and saved snapshot before delivery. Cross-owner job references are rejected. Workspace repositories reject unsupported update operators and aggregation stages that could join, merge, or output other collections.

The browser clears loaded workspace records, forms, and cached queries when the Firebase account changes or the API rejects the session. API responses captured under an earlier account are discarded after an account switch.

All authenticated management routes use owner-scoped repositories. Reads, updates, deletes, counts, upserts and aggregation require the authenticated user ID. There is no cross-workspace bypass for SUPER_ADMIN. Request bodies cannot set ownership, related records must belong to the same workspace, and workers propagate ownership into monitoring results, incidents and notifications. Unassigned legacy data stays hidden until an operator explicitly migrates it. Operators with direct database credentials still have administrative database access.

Public installations have per-workspace record and queue limits plus per-user and per-IP rate limits. Record limits are admission checks, not transactional billing quotas; concurrent writes can briefly exceed them. Enforce infrastructure budgets and egress limits appropriate to the hosting environment. Enable Firebase email enumeration protection and configure a Firebase password policy and signup abuse controls before opening registration. Rotate any service-account key previously shared in chat before publishing or deploying.

## Session expiry

The server enforces a fixed JWT expiry and a configured maximum session age; activity does not renew the session. The browser also clears workspace state when its server-provided expiry is reached. Logout clears authentication cookies and revokes Firebase refresh tokens/session cookies for that account across devices. Cookie-based writes require an exact allowed Origin and JSON payload; SameSite=Strict adds protection against cross-site requests. Deploy through the documented same-origin frontend API proxy so these cookies can be used securely.
